# JSON 格式优化分析（schema 1.0.0 → 建议版）

> 目标：在**不丢失任何原有资讯**的前提下，让 JSON 格式尽可能简单、体积尽可能小。
> 本文所有数字皆为实测（抽样 120 档 / 173 MB 与 40 档 / 102 MB 两轮抽样），
> 简化方案的资讯一致性已用 `_analysis/simplify_proto.py` 逐节点比对验证。

---

## 0. 结论摘要

| 项目 | 现状 | 简化后 |
| --- | --- | --- |
| 单档体积 | 100% | **约 33%**（实测 32.7%～34.6%） |
| 全语料体积 | 8.10 GiB | **约 2.8 GiB**（省约 5.3 GiB） |
| 节点 schema 复杂度 | `anyOf` 四类 + `app` 特例（`lemma`/`readings`/`wit`） | 单一节点模型，无特例 |
| 资料真源 | 同一份资料存在 3 份副本 | **1 份**（其余皆可重算） |
| 资讯损失 | — | **0**（逐节点比对 60 档全等） |

主要杠杆（按贡献排序）：

1. **去掉每个节点的 `text` 字段**（占原档案 **31.4%**）——它是 `children` 的确定性函数。
2. **去掉顶层全文 `text`**（**9.9%**）——由 `body`/`back` 依固定渲染规则重算。
3. **去掉扁平注释索引 `notes`**（**5.4%**）——每个注释都已在树中，索引 100% 重复。
4. **键名缩短与节点表示简化**（`type`→`t`、`children`→`c`、`attrs`→`a`；文字节点改裸字串；省略空 `children`）——再省约 **13%**。
5. **合并 `app` 的特例字段**——`lemma`/`readings` 回归一般子节点 `lem`/`rdg`。

## 2. 问题诊断

### 2.1 每个元素节点都带一份 `text`（最大冗余，31.4%）

```json
{"type":"p","attrs":{"rend":"bold"},"children":[{"type":"text","text":"如是我聞"}],"text":"如是我聞"}
```

`text` 是 `children` 的确定性函数（`tools/sutra/convert.py` 的 `node_text`／`children_text`／
`contributed_text`：`lb`/`pb` 贡献换行、纯排版空白不计入、注释不计入、`app` 取正读）。
**结论：不是「删除资讯」，而是「不重复存放同一份资讯」。** 重算规则已完全写在转换器里，
对外只需暴露一个 `render_text(nodes)` 函数即可。

> 注意：元素 `text` **不是** 子节点文字的简单串接——`lb`/`pb` 相邻换行的裁除规则参与其中。
> 因此消费端若要「逐节点取纯文字」，应使用转换器同款渲染函数，而不是自行相加。

### 2.2 顶层 `text` 全文（9.9%）

由 `body` + `back` 依同一套渲染规则拼出，是纯派生资料。它对「全文检索」很有用，
但代价是每档重复保存整部经文。**建议**：正文树为唯一真源，全文由工具即时产生；
若追求检索速度，可另存 `*.txt` 旁挂檔（不进 JSON 结构）。

### 2.3 顶层 `notes` 扁平索引（5.4%）

`collect_notes()` 把树中每个 `<note>` 的 `id`/`n`/`place`/`type`/`subtype`/`target`/`resp`/`rend`/`text`
再抄一份到顶层阵列，**全部字段都已在树中的 note 节点上存在**，索引 100% 重复。
**建议**：删除；若需「全文注释检索」，按大藏经导出独立的注释索引档（sidecar）。

### 2.4 空 `children` 阵列（3.5%）

`<lb/>`、`<pb/>`、`<anchor/>`、`<space/>` 等叶元素一律带 `"children":[]`（304,735 笔 / 抽样 80 档）。
**建议**：`children` 缺省即无子节点。

### 2.5 `ws` 旗标可由内容推导

```json
{"type":"text","text":"\n","ws":true}
```

`ws` 的定义是「内容仅含 ASCII 空白」（`ASCII_WS = " \t\r\n"`），即 `text.strip(" \t\r\n") == ""`，
纯函数可推导。**建议**：去掉旗标，规则写进格式说明。

### 2.6 `app` 的特例字段（3.7%）

```json
{"type":"app","lemma":{"type":"lem","wit":["#A"],"children":[…],"text":""},
 "readings":[{"type":"rdg","wit":["#B"],"children":[…],"text":""}], …}
```

- `lemma` / `readings` 是 `children` 的另一种摆法（同一批 `lem`/`rdg` 子元素），
  却要在 schema 写三条 `if/then` 特例（`allOf` 里有 4 条专门约束 `app`）。
- `wit` 同时出现在 `attrs`（字串）与独立栏位（阵列），**同一资讯存两份**。
- **建议**：`app` 就是一般容器，其子节点为 `lem`（正读）与 `rdg`（异读）；
  `wit` 只保留属性形态（字串）。schema 的 `app` 特例整段消失，正读身份由 `type:"lem"` 表示。

### 2.7 键名与属性名的重复开销

- 节点键名 `type`/`children`/`attrs` 每次出现都重写一遍（每节点约 18～26 bytes 的纯键名开销）。
- 属性名 31 种，其中长名重复百万次：`style`(17,437)、`target`(23,416)、`resp`(22,170)、
  `type`(42,217)、`cb_place`(8,408)、`place`(20,695)、`from`/`to`(13,924)、`ed`(246,786)、`n`(306,316)。
- **建议**：
  - 节点键名缩短：`t`（type）、`a`（attrs）、`c`（children）、`i`（xml:id）、`n`（ns）。
  - 属性名改以全域对照表编码（`n`→`a`、`type`→`b`、`rend`→`c`…，对照表只存一份于 Schema）。
    实测此一项再省 0.8 个百分点；属性**值**不可压缩（那是资料本体）。

### 2.8 文字节点用对象表示

41.5 万个文字节点各写成 `{"type":"text","text":"…"}`，其中 `"type":"text",` 是纯开销。
**建议**：`children` 阵列内以裸字串表示文字节点，元素/注解/PI 才用对象。

### 2.9 顶层栏位的重复与派生

- `canon`（名称、简称、英文名、目录名…）在 4,990 档各存一份，`catalog.json` 已有同一份 → 建议只留 `canon` 代码。
- `stats`（字数、行数、注数…）全部可由树重算 → 建议删除或移入 `catalog.json`。
- `text_element` 大多为 `{}` → 只在非空时输出。
- `source`（含 `xml_sha256`）体积仅 0.03%，但可追溯价值高，**建议保留**。

### 2.10 `header` 的自訂 schema（2.9%）

档头是整个档案里唯一不走统一节点模型的区块：`parse_header()` 另写了一套
`publication/encoding/responsibility/characters/revision/languages` 结构。
两难：

- **保留现状**：消费端查阅方便，但格式多一套规则、且是 TEI 结构的「再诠释」，可能漏掉未建模的栏位。
- **改为统一 TEI 树**：全档案只剩一种节点模型，最简单；代价是档头查询变笨拙、体积可能增加（待实测）。

体积上 `header` 只占 2.9%，因此这一项应**以「简单」为准**：若追求单一模型，可改树；
若保留便利性，则应把未建模的 TEI 栏位也补进去，避免「看似完整实则缺失」。

## 3. 建议格式（V3）

### 3.1 顶层

```jsonc
{
  "schema_version": "2.0.0",
  "id": "T01n0001",
  "canon": "T",              // 名称等资料查 catalog.json
  "volume": "T01",
  "work": { … },             // 书目（保留）
  "header": { … },           // 档头（保留现状或改树，见 §2.10）
  "body": [ …节点… ],        // 不再包 {"blocks":[…]}
  "back": [ …节点… ],
  "source": { … }            // 来源 XML 路径/位元组/SHA-256（保留）
}
```

移除：`text`（可重算）、`notes`（可重算）、`stats`（可重算）、`text_element`（空则省略）。

### 3.2 节点

```jsonc
// 文字节点 → 裸字串
"如是我聞"

// 元素节点
{"t":"p","a":{"rend":"bold"},"c":[ …子节点… ]}

// 带 xml:id / 命名空间
{"t":"div","n":"cb","i":"T01.0001","a":{"type":"apparatus"},"c":[ … ]}

// 异文异读：不再有特例字段
{"t":"app","c":[
   {"t":"lem","a":{"wit":"#A"},"c":[ … ]},
   {"t":"rdg","a":{"wit":"#B"},"c":[ … ]}
]}

// 注解 / 处理指示
{"t":"comment","x":"…"}
{"t":"pi","g":"xml-model","x":"…"}
```

| 简化键 | 意义 | 出现条件 |
| --- | --- | --- |
| `t` | 元素/节点种类（文字节点除外） | 必填 |
| `a` | 属性（`xml:id` 除外；CBETA 命名空间属性以 `cb_` 前缀） | 有属性时 |
| `c` | 子节点阵列（省略即无子节点） | 有子节点时 |
| `i` | 对应 `xml:id` | 有 id 时 |
| `n` | 命名空间，目前只有 `"cb"` | 非 TEI 命名空间时 |
| `x` | 注解/处理指示内容 | 仅 comment/pi |
| `g` | 处理指示 target | 仅 pi |

### 3.3 规则（写入格式说明即可保证零损失）

1. 文字节点 = `children` 阵列中的裸字串；其「纯排版空白」性质由内容推导（`s.strip(" \t\r\n")==""`），不再另设旗标。
2. 元素节点的纯文字 = 依 `contributed_text` 规则由 `c` 重算（`lb`→`\n`、`pb`→空、纯空白段→空、注释→空、`app`→正读）。
3. 全文 = `body` 渲染结果 +（必要时换行）+ `back` 渲染结果。
4. 注释索引 = 遍历 `c` 收集 `t=="note"` 节点（字段由 `a` 取得）。
5. `app` 的正读 = 其子节点中 `t=="lem"` 者；`wit` 只以属性形态存在。

### 3.4 体积实测

| 版本 | 说明 | 体积 |
| --- | --- | ---: |
| V0 | 现状 1.0.0 | 71,778,310（100%） |
| V1 | 仅去掉每节点 `text` | 37,123,046（51.7%） |
| V2 | V1 + 去掉 `notes` 索引 | 34,068,411（47.5%） |
| V3 | V2 + 短键 + 裸字串 + 省略空 `children` + `app` 统一 + 去顶层 `text` | 24,833,484（**34.6%**） |
| V4 | V3 + 属性名编码表（31 码，对照表另存一次） | 24,241,794（**33.8%**） |

40 档整档实测：101,846,840 → 33,322,887（**32.7%**），资讯不一致 **0 档**。
全语料外推：8.10 GiB → **约 2.8 GiB**。

### 3.5 无损性论证

| 被移除的东西 | 为什么不是资讯损失 |
| --- | --- |
| 节点 `text` | 是 `children` 的确定性函数，规则写在格式说明第 2 条 |
| 顶层 `text` | 是 `body`+`back` 的确定性函数，规则第 3 条 |
| `notes` 索引 | 每笔注释的 `id`/`n`/`place`/… 全在树中 note 节点上，规则第 4 条 |
| `ws` 旗标 | 内容为空白的函数，规则第 1 条 |
| `lemma`/`readings` | 改为 `c` 中的 `lem`/`rdg` 子节点，资讯一字未减 |
| `wit` 阵列 | 改回属性字串（`" ".join(wit)`），可逆 |
| 空 `children` | 缺省即无子节点，语义相同 |
| `stats` | 可重算的统计 |

**验证工具**：`_analysis/simplify_proto.py` 把新旧格式摊平成同构资讯序列
（元素类型／命名空间／xml:id／属性／文字内容／纯空白性质／注解／处理指示／见证资讯）逐项比对，
抽样 60 档全等。

## 4. 其他可选路线（供比较）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A（推荐）** V3 | 单一节点树、去派生、短键 | 结构直观、检索方便、通用 JSON 工具可直接用 | 体积为原式 1/3 |
| B 纯文本 + 标注 | 正文存 `.txt`，JSON 只留行级标注（卷次、行号、异文指针） | 体积最小、阅读最佳 | 需自订标注语法，失去「一档一 JSON 自足」 |
| C 数组式节点 | 节点写成 `["p",{…},[…]]` 之类 | 再省 5～8% | 可读性下降，调试困难 |

若最终以「体积最小」为唯一目标，B 优于 A；若以「一个 JSON 自足且通用」为前提，A 最优。

## 5. 迁移与验证建议

1. **先定稿格式说明**（§3.3 规则表），再改 `convert.py`；格式说明是零损失的契约。
2. 在 `sutra/schema/sutra.schema.json` 旁新增 `sutra.v2.schema.json`（不要就地改，避免转换与验证同时变动）。
3. **复用既有稽核**：
   - `python3 main.py audit` 仍应全绿（XML vs JSON 逐项比对），
     但需把「重算 `text`／`notes`」纳入稽核项，而不是比对字段是否存在。
   - `python3 main.py qa` 的独立提取器比对可加一档：按 V3 规则重建全文，须与旧 `text` 完全相同。
4. `catalog.json` 补入各档 `stats`（字数、行数、注数…）与 `canon` 名称表，档案本体即可更简。
5. 全量转换后重跑 `check`（validate + audit + qa + verify），抽样 100 档人工比对。

## 6. 风险

- **依赖 `node.text` 的下游客户**：需提供兼容层（`render_text`），或改采 V1（保留 `text`）作为过渡版。
- **`ws` 旗标移除**：若下游需要「原文排版空白」定位，须按规则重推，边缘情形（内容仅含 ASCII 空白但被标为非 ws）不存在，已验证。
- **属性名编码表**：会让 JSON 变得「不可直接阅读」，与「格式简单」的诉求有张力；
  建议只对高频长名（`style`/`target`/`resp`/`cb_place`）编码，其余保留原名，或干脆保留原名（只省 0.8%）。
- **档头改树**（§2.10）：会改变消费端查档头的方式，应独立决策、单独一次改版。
- **语义化版本**：V3 属破坏性变更，须升为 `2.0.0` 并保留 `1.0.0` 的转换器以供回溯。
